# F-A11Y-002 — Dynamic type

Status: done | Priority: P1 | Phase: 6
Reads: 24-DESIGN-SYSTEM#accessibility-baseline

## Spec

Full functionality at 200% system text scale. This constrains how many columns
the set row can carry, which is why it's a design constraint from the start
rather than a later fix.

## Status note

Batch 6.1 covered `ActiveWorkoutScreen` and `ExerciseDetailScreen`. This pass
closes the rest: every other reachable screen in the app now has its own
200%-scale render test asserting no `FlutterError` overflow, following the
same pattern — `DashboardScreen`; `HistoryScreen`, `WorkoutDetailScreen`,
`EditPastWorkoutScreen`; `RoutineListScreen`, `RoutineEditorScreen`,
`RoutineDayEditorScreen`, `StarterProgramGalleryScreen`;
`ExerciseCatalogScreen`, `ExerciseEditorScreen` (both create and edit mode);
`ConsistencyScreen`, `PrTimelineScreen`, `InsightsScreen`; `BodyWeightScreen`,
`ProgressPhotosScreen`; `StartWorkoutScreen`, `SessionSummaryScreen`;
`OnboardingScreen`; and all nine of Settings' screens. `PlaceholderScreen` is
the one screen file left untested — grepping `lib/` for its constructor
turns up no call site at all; every tab has had a real screen since Phase 1,
so it's dead code, not an unaudited one, and removing it is a one-line
cleanup outside this feature's own scope.

The audit found two real, previously undiscovered overflow bugs, both fixed
in the same pass rather than just documented: `AppearanceScreen`'s "ghost
values" preview used a bare `Row` for two side-by-side strings that overflow
horizontally once both are long enough at 200% scale — now a `Wrap`, the
same widget the swatches immediately above it already used for the identical
reason. `OnboardingScreen`'s welcome page (built in batch 6.3, days before
this audit) centred its content in a fixed, non-scrolling `Column` — the
icon plus three text blocks overflow vertically at 200% — now a
`SingleChildScrollView`, matching the other two onboarding pages, which were
already `ListView`s and never had the problem.
