# F-I18N-001 — String externalisation

Status: in-progress | Priority: P1 | Phase: 6
Reads: 22-UNITS, 24-DESIGN-SYSTEM

## Spec

All user-facing strings in ARB files from the start, even while English-only.
Retrofitting extraction across a finished app is miserable and never quite
complete; doing it continuously costs almost nothing.

## Status note

Batch 6.2 migrated `SettingsScreen` alone as the first proven slice. This
pass adds four more: `DashboardScreen` and `HistoryScreen` (two of the five
tab-root screens), `RoutineListScreen` (a third, plus the shared
`promptRoutineName` rename/create dialog it defines and every other routines
screen calls), and `ConfirmSheet` — the one confirmation sheet every
destructive action in the app goes through, so its default `confirmLabel`/
`cancelLabel` moved from a literal parameter default (Dart requires those to
be compile-time constants, which a `BuildContext`-resolved string can't be)
to a null default resolved from `AppLocalizations` in the function body.
ICU plurals (`{count, plural, one{...} other{...}}`) cover exercise counts
on both the dashboard's and history's workout tiles — two separate ARB keys
with identical English text, matching this file's own existing
per-screen-prefix convention rather than introducing a shared, unprefixed
key. Deliberately not touched: `AppShell`'s bottom-navigation labels are a
`static const List<ShellDestination>` — a compile-time constant an existing
test (`navigation_test.dart`) asserts against directly — and turning it
into something `AppLocalizations`-aware needs a real restructure (an
instance getter or a `BuildContext` parameter), not a mechanical
find-and-replace, so it's left for a batch that can give it its own
attention rather than folded in here as a side effect. Found and preserved,
not silently fixed: the routine-delete confirmation message contains a
literal internal doc citation, `` (`ADR-0004`) ``, that reads as broken copy
to a real user — moved into ARB verbatim rather than quietly rewritten
mid-migration, with a follow-up task filed to fix the copy itself
separately. Every other screen — catalogue, insights, the rest of routines,
the rest of logging and history, body, all of analytics beyond what's
covered — is still English-string literals, left for future batches.

A further pass added the last two tab-root screens: `ExerciseCatalogScreen`
(including the archive-by-equipment flow's plural+placeholder combo,
`{count, plural, =0{Nothing to archive.} one{...} other{...}}` — the ICU
zero-selector handling both the empty-result and normal-count cases in one
key rather than a separate literal check) and `InsightsScreen`, by far the
largest single-screen migration yet (over 40 keys: every section heading,
empty/insufficient-data state, explanatory paragraph, and the
`RangePreset`/rep-range-bucket-adjacent prose). Deliberately left as
literals within `InsightsScreen`, on the same reasoning `docs/22-UNITS.md`
already applies to unit symbols: the rep-range (`1–3`, `21+`) and
intensity-zone (`<60%`, `90%+`) bucket labels, and every chart
`valueLabel`/axis formatter closure (`'${v} min'`, tabular percentages) —
these read as formatted numeric ranges, not translatable prose, the same
category this file already excludes `QuantityFormatter` output from.
`date_range_selector.dart`'s own chip labels are a separate widget file
this pass didn't touch, so the range-preset prose now exists in ARB twice
under different names for the two different places it's read from
(`InsightsScreen`'s own `_rangeLabel` vs. the selector's chips) — a
duplication to reconcile if that selector is migrated later, not a bug now.

All five tab-root screens (Dashboard, Routines, Start, History, Insights)
are now migrated at their top level; `ExerciseCatalogScreen`, reached from
Dashboard, makes it six real screens deep.

The next pass closed out the rest of the logging feature:
`ActiveWorkoutScreen` (the app's densest screen — every dialog, sheet,
overflow-menu item, and both plural-with-independent-variables messages,
e.g. `"{exercises, plural, ...} and {sets, plural, ...} will be removed
..."`, a single ARB message with two independent ICU plural clauses),
`StartWorkoutScreen`, and `SessionSummaryScreen`. Deliberately not
followed into shared widgets `ActiveWorkoutScreen` itself only *uses* —
`SetRow`, `AddSetButton`, `RestTimerBar`, and `fieldHeader()`
(`set_value_format.dart`, called from three separate presentation files,
none of which take a `BuildContext` where it's needed) — each is its own
unit with its own call sites across multiple screens, the same "needs a
batch of its own attention" reasoning already applied to `AppShell`, not a
mechanical extension of migrating the screen that happens to render them.

A further pass migrated `RoutineEditorScreen` (both the multi-day list and
the single-day-collapses-inline case, `F-ROU-002` §4), reusing several
keys `RoutineListScreen`'s own migration already defined
(`routinesDeleteConfirmTitle`/`Message`, `routinesDuplicateAction`,
`routinesArchiveAction`, `routinesDeleteAction`, `routinesNoDaysYet`)
rather than duplicating near-identical text under a new prefix — the
per-screen-prefix convention this file otherwise follows is a default for
independent copy, not a rule against reuse when two screens are genuinely
describing the same action. One consequence worth naming: this screen's
own routine-delete message was already clean prose with no `ADR-0004`
citation, unlike `RoutineListScreen`'s version — reusing
`routinesDeleteConfirmMessage` here means both call sites now show the
citation-bearing text until the filed follow-up task fixes the ARB value
itself, at which point both correct simultaneously from one edit.
`RoutineDayEditorScreen` — 1,000+ lines, several complex sub-widgets (the
five-segment progression target sheet, superset grouping, the preview
card, the weekday scheduler `RoutineEditorScreen` itself already imports
from this file) — is deliberately left for its own batch rather than
folded in as a continuation; it is large enough to be its own unit of
work by this file's own established sizing (`InsightsScreen` was the
previous largest single migration, at roughly 700 lines).

Still English literals: `RoutineDayEditorScreen`, the rest of history
(detail, edit), body, `ConsistencyScreen`/`PrTimelineScreen`, every
Settings sub-screen beyond the root, `AppShell`'s nav labels,
`SetRow`/`AddSetButton`/`RestTimerBar`/`fieldHeader()`, and onboarding.

A sixth pass took on `RoutineDayEditorScreen` itself — the file this batch's
previous status note singled out as its own unit of work — plus the shared
free function it and `RoutineEditorScreen`'s `_DayTile` both call,
`formatScheduledWeekdays`. That function's weekday abbreviations were a
module-level `const List<String>` (`_weekdayAbbreviations`), which — unlike
a `BuildContext`-having widget's `build()` — has no `AppLocalizations` to
read from at the point it's defined. Rather than thread a `BuildContext`
through a pure formatting function, `_weekdayAbbreviations` became
`weekdayAbbreviations(AppLocalizations l10n)`, a small function callers
resolve once and pass into `formatScheduledWeekdays(weekdays,
abbreviations)` alongside the data — the function itself stays pure and
independently testable, just no longer hard-coded to English. Both real
call sites (the weekday-scheduler sheet's own chip row, and
`RoutineEditorScreen`'s `_DayTile`) updated accordingly. The rest of the
screen — the target-editor sheet's five progression-rule segments and their
per-rule field sets, the superset multi-select bar (including its ICU
plural, `"{count, plural, one{1 selected} other{{count} selected}}"`), the
`_RoutinePreviewCard`'s duration/volume labels, and the "already training"
resume sheet — is now fully migrated, closing the file this batch's
previous note called out as too large to fold into a continuation. Several
keys are deliberately reused rather than duplicated under a new prefix, the
same judgment call the fifth pass made for `RoutineEditorScreen`:
`routineEditorScheduleAction`/`routineEditorMenuRename`/
`routineEditorExercisesReadError`/`routineEditorRenameDayTitle` (exact-text
matches already defined for the parent screen), `routineNameDialogSave`/
`routineNameDialogCancel` (this app's only existing generic Save/Cancel
pair, originally scoped to the rename/create-routine dialog but genuinely
the same action here), and `startWorkoutAlreadyTrainingTitle` for the
already-training sheet's title — its *message*, unlike `StartWorkoutScreen`'s
version, has no workout name available at this call site
(`ActiveWorkoutExistsException`'s catch block only knows a conflict
happened, not which workout won it), so the message itself is a new key,
`routineDayEditorAlreadyTrainingMessage`.

Still English literals: the rest of history (detail, edit), body,
`ConsistencyScreen`/`PrTimelineScreen`, every Settings sub-screen beyond the
root, `AppShell`'s nav labels, `SetRow`/`AddSetButton`/`RestTimerBar`/
`fieldHeader()`, and onboarding.
