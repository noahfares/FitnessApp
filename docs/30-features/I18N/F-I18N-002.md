# F-I18N-002 — Locale-aware formatting

Status: done | Priority: P1 | Phase: 0
Depends on: F-SET-001
Reads: 22-UNITS, 24-DESIGN-SYSTEM

## Spec

1. Numbers formatted via `intl`, honouring the locale's decimal and grouping
   separators. `QuantityFormatter` in `lib/core/formatting/`.
2. **Parsing is lenient about which separator the user types.** A US user typing
   `102,5` means 102.5, and refusing that is a bug. `QuantityParser`.
3. Where a separator is genuinely ambiguous, the locale decides: the group
   separator followed by exactly three digits reads as grouping (`1,234` is 1234
   in en_US), otherwise as a decimal point (`102,5` is 102.5).
4. Malformed input returns null rather than a guess. Letters are rejected, never
   stripped — silently discarding characters is how `10O` becomes 10.
5. Dates deferred until a screen displays one; the parser is the correctness
   risk and it is done.

## Acceptance

- [x] `102,5` and `102.5` both parse to 102.5 in en_US and de_DE.
- [x] `1,234` is 1234 in en_US and 1.234 in de_DE; `1.234` is the mirror image.
- [x] Formatter output matches every row of the display table in
      [`../../22-UNITS.md`](../../22-UNITS.md), in both unit systems and both
      locales.
- [x] Format-then-parse round-trips a value unchanged, in both locales.

## Edge cases

Trailing separator (`102.`), lone separator, two decimal points (`1.2.3`),
invalid grouping (`1,23,456`), scientific notation — all rejected. Mixed
separators (`1,234.5`) take the last as the decimal point.
