# F-CAT-001 — Seeded exercise catalogue

Status: done | Priority: P0 | Phase: 1
Blocks: F-CAT-002, F-LOG-002
Reads: 21-DATA-MODEL#exercises, 21-DATA-MODEL#seed-data, 10-VISION#risks
Data: `exercises`

## Spec
1. Catalogue ships as `assets/seed/exercises.json`, versioned, each record with
   a stable UUID, the source dataset's `external_id`, name, primary muscle,
   secondary muscles, equipment, and tracking type.
2. Seeded into `exercises` on first launch.
3. On app upgrade, re-seeding matches on `external_id` — adding new records and
   updating unmodified seeded ones. It never overwrites user-edited or custom
   rows. Matching on `external_id` rather than name is what makes upstream
   corrections possible without duplicating rows or breaking references from
   existing sets.
4. `assets/seed/SOURCES.md` records provenance and licence for every record.

## Acceptance
- [x] First launch yields a populated catalogue with no network access —
      100 exercises, seeded before the first frame.
- [x] Every record has a primary muscle and a tracking type — no nulls.
      Parsing is strict: an unknown enum value throws rather than defaulting.
- [x] Editing a seeded exercise, then upgrading, preserves the user's edit.
- [x] An upstream rename applied via `external_id` updates the row without
      creating a duplicate or orphaning historical sets.
- [x] `SOURCES.md` accounts for every record with a verified licence.

## Edge cases

Seeding interrupted mid-write (wrap in a transaction). A seeded
exercise removed in a later version but referenced by existing sets — archive,
never delete.

## Resolved questions

- **Source — settled: hand-authored.** The Free Exercise DB lead could not be
  verified; its licence file was not retrievable at the expected path, and an
  unverifiable licence is not a licence. Given this entry calls unverified
  content "fatal to a store release", hand-authoring was the only defensible
  option. It also proved better on the merits — correct muscle assignments
  matter because `F-ANA-005` aggregates over them. Full reasoning:
  [`assets/seed/SOURCES.md`](../../../assets/seed/SOURCES.md).
  **This closes the largest legal risk in the project.**
- **"User-modified" — settled: a `seed_updated_at` column** (schema v2).
  Seeding stamps it alongside `updated_at`; a row is user-edited when the two
  differ. The obvious alternative — comparing `updated_at` to `created_at` —
  was implemented first and is wrong: it works for exactly one re-seed, after
  which every row looks edited and upstream corrections silently stop applying.
  A test covers three consecutive re-seeds.

## Implementation

- `assets/seed/exercises.json`, generated by `tools/gen_seed_exercises.py`,
  which validates every muscle and equipment value against the enums and
  rejects duplicates. UUIDs are `uuid5`-derived from `externalId`, so
  regenerating never changes a row's identity or orphans logged sets.
- `lib/data/seed/exercise_seeder.dart` — matches on `external_id`, applies in
  one transaction, reports inserted/updated/skipped so a silent no-op is
  distinguishable from a silent failure.
- Runs before the first frame in `main()`, so the catalogue is never briefly
  empty.

---

## Why

The app is unusable on first launch without a decent set of
exercises. 200–400 covers essentially all barbell, dumbbell, machine, cable and
bodyweight work an ordinary lifter does. This is also the single largest legal
risk in the project: scraping a competitor's database is a non-starter and would
be fatal to a store release.
